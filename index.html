What the estimator fits
Fig. 2. A Thevenin equivalent circuit, shown here as the 2RC case; the estimator fits 1RC to 5RC. OCV(z) is the open-circuit voltage as a function of state of charge z; each RC pair has a time constant tau = R·C.

A battery management system predicts cell voltage, state of charge and available power from a model. The model needs values for R0, the RC pairs, open-circuit voltage as a function of state of charge, and hysteresis. Those come from bench tests on real cells, and most of the work is in getting them out of the raw data.

The test itself arrives as a spreadsheet written for people: headings vary between suppliers, cutoff criteria are free text, steps repeat by reference, and cells are merged down whole blocks. On the measurement side, sign, unit and capacity errors never crash anything; they produce a plausible chart with the wrong answer. And the quantities are small. Hysteresis is typically 5 to 30 mV, sitting under an I·R overpotential three to six times larger, so measuring it in the wrong place gives you the overpotential.

What I built

Four tools. Each runs on its own, and the first can drive the other three.

ToolWhat it does
doe_visualizerParses a design-of-experiments (DOE) spreadsheet into the current-versus-time waveform the cycler will run, so a test can be checked before a cell goes on a channel. Hosts the interactive analysis, modelling and estimation tabs (Streamlit).
dcir_analysisAverages per-cell DCIR sweeps, splits charge from discharge, holds three factors and sweeps the fourth, cross-checks every row against Ohm's law, and writes a plain-language sensitivity report.
hml_analysisCoulomb-counted SOC, OCV at every relaxation, and the charge/discharge hysteresis loop per SOC. Ships a cell simulator so the analysis can be validated against known truth.
parameter_estimationSegments arbitrary pulse data (Fig. 1), then fits a shared 1RC to 5RC Thevenin model across all pulse windows by bounded nonlinear least squares, with holdout scoring and per-parameter standard errors.

The two analysis backends cannot share a Python process: both define a top-level utils, and whichever loads first wins without an error. So the hub runs them as subprocesses behind a versioned CSV-plus-manifest contract, and integration tests launch the real backends in CI so that a column rename on either side fails there instead of in the app. The DOE parser handles merged cells, non-unique step numbering and repeat-by-reference; misreading an 86-hour test by one repeat is three and a half days of channel time.

Stated limitations

No real cell data is included; every dataset is simulator output, and the simulator is not fitted to any measured chemistry, so recovery on real data will be worse. Coulombic efficiency is assumed to be 1 and nominal capacity is an input. The fitted model has no temperature dependence and no hysteresis state. Only DCIR and HML (the hysteresis tool) have analysis backends, and ageing is out of scope. The theory, the worked examples behind every number above, and the architecture are documented in the repository.

UI Element Scraper

A Java tool that signs into a web application and crawls it depth-first, producing a spreadsheet of every interactive control it can reach, including the ones behind a modal, a tab or a dropdown.

Writing a UI test suite starts with an inventory: what is on this page, how do I address it, and what should I assert about it. Built by hand that inventory is slow and systematically incomplete, because the controls people miss are the ones hidden behind an interaction. A confirm-delete button inside a modal is both the hardest element to notice and one of the most important to cover.

The crawler searches the graph of UI states, not the DOM tree: nodes are page states, edges are clicks. Depth-first suits this graph because reaching a state is expensive (a click, a wait, an animation) while backtracking within one is cheap, so it is worth exhausting a modal before opening the next. Breadth-first would re-open the same containers repeatedly.

Termination on a cyclic, effectively unbounded graph

The crawl cannot finish by exhausting the graph, so it finishes by four independent bounds:

  • A depth cap: the number of interactions needed to reach an element, where zero is the initial page.
  • A per-trigger visit set, keyed on a stable generated identifier rather than a transient element reference. This is the actual cycle-breaker.
  • A per-element identity set.
  • A global element budget, as a hard stop.

The report has one row per control: context (page, modal, tab), depth, tag, the best human-readable name, raw attributes, an XPath anchored on a stable id where one exists, and type-aware suggested test cases. A summary sheet adds counts and a locator-quality breakdown, the share of stable versus positional XPaths, which says whether a suite built on the inventory will survive the next refactor. Distinct exit codes per failure class let a pipeline tell why a run failed without parsing logs.

A companion layer that consumes the inventory, exercises each control and reports pass or fail was started and is still in progress, developed alongside a senior engineer.
