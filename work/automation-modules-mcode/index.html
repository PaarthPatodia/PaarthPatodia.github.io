The shared shape

Across the four engagements the recurring piece was the same: connect a model to enterprise data or an operational channel through n8n, normalise what comes in, validate what comes out, and route the result somewhere a team already looks. Reusable structured-output validation, API error handling, workflow monitoring and test cases sat under all of it, so malformed model or external-service responses were rejected rather than passed downstream.

In detail: a natural-language manufacturing intelligence agent

Client and purpose. Subros Limited, a manufacturer. Plant teams wanted to ask questions about production and quality in plain language instead of raising manual MIS requests, and to receive shift-level reports without assembling them by hand.

What I built. The n8n orchestration and data-processing layer of the agent: a webhook trigger that receives the query; Code nodes that normalise the request and validate the model's response; Switch and IF nodes that route by query type and on failure; and HTTP Request nodes that call internal services and model endpoints. The data the workflow operated on was ERP-derived (SAP-sourced) production and quality data exposed to it by the platform. I also developed workflow components for automated shift-level production and quality reporting, which transformed that data into structured summaries and routed them to engineering and operations teams through existing enterprise channels.

What I did not build. The SAP connector, the SAP-side MCP server and the ERP integration were the team's. I consumed ERP-derived data exposed to my workflow; I did not configure SAP, write ABAP, or have unrestricted SAP access. SAP is not a skill I claim.

Reported outcome. The project team reported that the deployment cut recurring operational query turnaround from up to one working day to seconds across three departments. That figure was reported at the overall project level by the team and client; I contributed modules to the deployment and did not design or measure the figure.

Engineering decisions

Structured output is enforced, not requested

Asking a model to "return JSON" is not validation. Each extraction module defined a field schema and checked every response against it programmatically: type, presence and range. A response that failed went down a retry path with the failure described; a response that failed again raised an exception into monitoring rather than passing partial data downstream. This is the single pattern that most reduced silent failures.

Normalise at the edge

Incoming data (a plain-language query, a voice transcript, a platform's analytics payload) was normalised into a fixed record as the first step, so every downstream node saw one shape. Routing decisions were then made on that record, not on raw input.

Feedback through context, not training

For the content pipeline, "learning from performance" meant retrieving metrics, normalising them, and injecting a compact summary of what performed well into the next generation prompt. It was deliberately not fine-tuning or online learning, and it is described that way.

Deliver where people already look

Outputs were routed into channels teams already used (enterprise messaging, an operations tracker, existing reporting lines) rather than into a new interface, which is why a voice message on WhatsApp could become a structured ticket without the operator changing anything.

Validation

At module level: test cases for the validation and error-handling paths (well-formed, malformed, incomplete and type-invalid responses; API errors and timeouts), and workflow monitoring so failures surfaced rather than vanished.
