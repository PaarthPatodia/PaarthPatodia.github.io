UI Element Scraper

A Java tool that signs into a web application, crawls it depth-first through modals, tabs and menus, and writes a spreadsheet of every interactive control it reached, each with a stable locator and suggested test cases.

Role
Designer and builder of the crawler and inventory. A companion test-execution layer was started with a senior engineer and is unfinished.
Origin and dates
Began as QA tooling during the Cardbyte internship (July to August 2025); developed into a standalone open-source tool.
Stack
Java 11+, Selenium 4 (driver resolved by Selenium Manager), Maven, Apache POI for Excel output
Repository
github.com/PaarthPatodia/ui-element-scraper, MIT licence
Repository on GitHub Design decisions Architecture

Key result

Run for this page against a small local demo application (a sign-in page and a contacts page with a modal, a tab set and a menu), the crawler inventoried 30 controls in 33 seconds at depth 1. Twenty of them existed only after a click: twelve inside the modal, five in the hidden tab, three in the menu. A flat scan of the loaded page would have recorded ten.

Every locator in the run was anchored on a stable id. On a real application that share is the most useful number in the report: it says whether a test suite built on the inventory will survive the next refactor.

Problem

Writing a UI test suite starts with an inventory: what is on this page, how do I address it, and what should I assert about it? Built by hand, that inventory is slow and, worse, systematically incomplete. The controls people miss are the ones hidden behind an interaction. A confirm-delete button inside a modal is simultaneously the hardest element to notice and one of the most important to cover.

At Cardbyte I was specifying test scenarios and then reviewing, debugging and modifying Selenium and TestNG scripts inside an existing Page Object Model framework. The inventory problem came up on every new page, so I built a tool for it.

What I built

The tool drives a real browser, so it sees what a user sees, and it clicks its way into modals, tabs and menus so those controls end up in the report. It produces a workbook (or a CSV, for diffing two runs) with one row per element: where the crawl was rooted, how the element was reached (page, modal: Add contact, tab: Billing), how many interactions were needed, the tag and raw attributes, the best human-readable name (text, then aria-label, title, label, placeholder), an XPath anchored on a stable id where one exists, and type-aware suggested test cases. A summary sheet counts elements by tag, input type, context, depth and ARIA role, and reports the share of stable versus positional locators.

Configuration resolves from command-line flags, then SCRAPER_* environment variables, then a properties file, so a CI job can run it with no file on disk and credentials never in the repository. Distinct exit codes per failure class (configuration, authentication, navigation, report) let a pipeline tell why a run failed without parsing logs. A --dry-run validates everything and exits before touching a browser.

Engineering decisions

Depth-first, because reaching a state is the expensive part

Reaching a new UI state costs a click, a wait and an animation; exhausting the state once you are in it costs almost nothing. So it is worth recording everything inside a modal before opening the next one. Breadth-first would re-open the same containers repeatedly. Depth is also the single biggest lever on runtime, which is why it is the first thing the README tells you to tune.

Termination on a graph that has no end

The UI state graph is cyclic and effectively unbounded, so the crawl cannot finish by exhausting it. It finishes by four independent bounds: a depth cap; a per-trigger visit set, keyed on a stable generated identifier rather than a transient WebElement or DOM reference, which is the actual cycle-breaker; a per-element identity set that stops the same control being recorded twice; and a global element budget as a hard stop.

Recovery depends on what the click did

After each click the crawler classifies what happened. A modal, tab or menu is recursed into and then closed or restored. A navigation is undone with browser back. A new window is closed and focus restored. A page that changed in place is re-scanned and reset. A click that did nothing observable simply continues, with no reset, because resets are what make crawls slow. An --always-reset flag exists for applications where that optimism is wrong.

Heuristics as pure functions

Element naming, locator construction and test-case suggestion all operate on an immutable ElementSnapshot rather than on live browser objects. That is why the unit tests run in about a second with no browser and no network.

Design mine, boilerplate assisted

The crawl strategy, the state graph, the termination bounds and the recovery paths are my design and I can defend each choice. The Selenium boilerplate underneath was AI-assisted, which I say plainly because the résumé lists Java as familiar rather than expert.

The five clicks that "did nothing observable" were the two navigation links' duplicates, the People tab (already selected), and the Edit and Delete buttons, which in the demo app have no handlers. The one that "navigated away" was the Settings link; the crawler went back and continued.

One honest wrinkle the run exposed: the name heuristic for a <select> without its own label text falls through to the visible option text, so the Team control was named "Engineering Sales" and Currency "USD INR EUR" in the raw workbook. The table above uses the label names; the downloadable workbook is unedited.

Validation

Two kinds. The unit suite, 217 tests, runs in about a second with no browser, because the crawler's heuristics are pure functions of an immutable element snapshot; mvn verify adds a coverage gate and packaging, and both run in CI on every push. The end-to-end check is a real crawl like the one above: the log states how many elements were captured before and after de-duplication, which triggers were activated or skipped, how many errors were recovered, and what each click did, so a run can be judged against what the page was known to contain.

Limitations and status

  • The crawler and inventory are complete. The companion test-execution layer, which would consume the inventory, locate and exercise each control and report pass or fail, was started with a senior engineer and is not finished. It is not part of the public tool and I do not claim it.
  • The login step expects a conventional email-and-password form; applications with SSO, MFA or CAPTCHA need the selector lists in LoginService extended or a pre-authenticated session.
  • The tool clicks every control it finds, including destructive ones. It should run only against systems you own or have written permission to test, and preferably against staging. The repository's SECURITY.md spells this out.
  • Runtime grows steeply with depth; depth 2 is tens of minutes on a typical application and depth 3 can be hours.
